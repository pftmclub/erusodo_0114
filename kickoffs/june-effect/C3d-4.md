## The problem

C3d-3 ported the engine side of June's RT_BOUNDING reaction (user case, five `CX2GUUser::JuneBounding*` handlers, `JuneInitBoundingStates`,
NPC half, last attacker). **No class registers the three `USI_BOUNDING_*` states**, so every RT_BOUNDING hit is ignored (logged once).

- June registers them in each class's own InitState from `<prefix>DAMAGE_BOUNDING_DOWN / _LANDCRASH / _UP` tables that sit **inline in each class script**
  (`june_src_fixed/data036_kom/<class>.src.lua`; nine March classes: prefixes ESSI_ AVSI_ LESI_ RSI_ ENSI_ CSI_ ASI_ ESI_ ANSI_). The 27 tables are identical
  across classes apart from the prefix and Elsword's `EFFECT_SET_LIST` (JUNE_BUGS 140).
- March's nine class scripts exist **only as bytecode** in `kom_contents/data036_kom/` (no `.src.lua`).
- **User rule (2026-10-09):** never invent a new `.lua` file (C3d-3's `June_Bounding_States.lua` was rejected and removed). Editing an existing Lua needs the user's go-ahead.
  If a route needs reasoning beyond the model, say so.
- No March DamageEffect or monster uses RT_BOUNDING, so nothing reaches the reaction on March data today; June data that does is not yet adopted.
