## The problem

C3d-3 ported the engine side of June's RT_BOUNDING reaction (user case, five `CX2GUUser::JuneBounding*` handlers, `JuneInitBoundingStates`,
NPC half, last attacker). **No class registers the three `USI_BOUNDING_*` states**, so every RT_BOUNDING hit is ignored (logged once).

- June registers them in each class's own InitState from `<prefix>DAMAGE_BOUNDING_DOWN / _LANDCRASH / _UP` tables that sit **inline in each class script**
  (`june_src_fixed/data036_kom/<class>.src.lua`; nine March classes: prefixes ESSI_ AVSI_ LESI_ RSI_ ENSI_ CSI_ ASI_ ESI_ ANSI_). The 27 tables are identical
  across classes apart from the prefix and Elsword's `EFFECT_SET_LIST` (JUNE_BUGS 140).
- March's nine class scripts exist **only as bytecode** in `kom_contents/data036_kom/` (no `.src.lua`).
- **User rule (2026-10-09):** never invent a new `.lua` file (C3d-3's `June_Bounding_States.lua` was rejected and removed). Editing an existing Lua needs the user's go-ahead.
  If a route needs reasoning beyond the model, say so.
- No March DamageEffect or monster uses RT_BOUNDING, so nothing reaches the reaction on March data today; June data that does is not yet adopted.

## Task

Find the best way to give the nine classes their bounding tables, and recommend one to the user. Weigh at least these routes, each against the rules above,
risk of a silent regression, effort, and whether the work is thrown away later:

1. **Inline edit of the nine March class scripts** (June's own layout): decompile, append the three tables byte-for-byte from `june_src_fixed`, recompile, re-add the
   nine `JuneInitBoundingStates( "<prefix>" )` calls. Needs the user's yes for editing existing Lua. Settle Ara first: find the differing constructor, and every reader
   of that table (`pairs` / `next` / `#` on it in Lua, or C++ reads of it), and say whether its order can matter.
2. **Leave it to the character ports.** The user ports June's class scripts (`JUNE2017_CHARACTER_PORT_CHECKLIST.md`; checklist 7l already lists this registration).
   If the June class scripts replace March's wholesale, an inline edit now is throwaway. Check what the checklist and the asset/lua port plans say about when
   March's nine class scripts get June's versions, and whether D10 (a) still requires C3d to do it.
3. **Byte-level append without decompiling** (e.g. splice a compiled chunk into the existing bytecode). Judge feasibility and risk; do not prototype it on a live file.
4. **Ship the class scripts as (XOR-encrypted) Lua source instead of bytecode** (user, 2026-10-09: this engine used to read encrypted plaintext Lua; bytecode
   only arrived with the March snapshot). Facts to start from: `X2OPTIMIZE_APPLY_UNPACK_HACK_PREVENTION` (`KTDXLIB/KTDX.h:393`) turns on LuaJIT, but
   `X2OPTIMIZE_REMOVE_LUA_INTERPRETER_MODULE` is defined only under `_SERVICE_` / `_IN_HOUSE_SERVICE_READY_QA_` (`KTDX.h:398-400`), neither of which this build
   defines, so the full parser is linked (`luajitLib` `Release`, CLAUDE.md *Toolchains*); the offline server-Lua tables already load as XOR'd plaintext
   (`DoMemory` / `DoMemoryNotEncript`, e.g. `X2Lib/Offline/X2OfflineStatTable.cpp`). Settle with code, not assumption: the exact load path a class script takes
   (`CX2UnitManager::CreateUnitLuaSpace` -> `CKTDXApp::LoadAndDoMemory` -> `KGCMassFileManager::LoadDataFile` with `X2OPTIMIZE_ENCRYPT_AFTER_COMPRESS`), whether
   it accepts source text, and what `kom.py pack` / elstools do with a plaintext `.lua` entry (manifest algo `"2"`). Also check whether an older (January / pre-March)
   kom still carries the class scripts as studio plaintext, and how that text compares with the March bytecode (a real original would beat a decompile).
   This route removes the recompile step but still edits an existing class script, so it also needs the user's yes.
5. **Any other route** that keeps the tables in the class scripts and needs no invented Lua and no hard-coded state data in C++ (hard-coding the tables is the
   band-aid CLAUDE.md forbids).
