## Task

**The problem.** March cuts each kom member name to 59 characters when it reads the XML manifest (`MASSFILE_NAMESIZE` 60,
`KTDXLIB/KGCMassFileManager.cpp:1880-1895`, `WCHAR_DIR` on). `LoadDataFile`'s live path (the `#else` of `MASS_FILE_FIRST`, about
`:915`) looks a file up by its full uppercased name, so any name over 59 characters is never found. 5 June assets are affected (listed in
Established facts).

1. **Design check first** (record it in the Done note):
   - every user of `MASSFILE_NAMESIZE` and `strFileName`: the XML read, the map insert at `:504`, `GetFileName` (`:1653-1692`), the
     packer paths `:2981` / `:3233`, and every copy of `MASSFILE_MEMBERFILEINFO`;
   - whether the V.0.1/V.0.2 binary member header on disk uses the 60-char size.

   If it does, do not grow the struct. Key long names through a side map instead, filled from the full XML attribute.
2. **Port behind the flag.**
   - Store and look up members by their full uppercased name.
   - A name of 59 characters or fewer must take exactly the old path.
   - Log `[KOM_LONG] <kom> <name>` once per long name registered.
   - Original code stays in `#else`.
3. **Check the encoding of `KGCMassFileManager.cpp` first.** If it is CP949, edit it with `tools/bytepatch.py` only.

**Done means:**
- flagcheck PASS;
- `build.py --deploy` with its `DEPLOY OK` line in the Done note;
- `kickoffs/june-asset-extract/X4-review.md` is written;
- the STATUS rows are updated.

There is no play-test here. The long-name files are staged in X5, so the hand-off says the flag is inert until X5 packs one.
